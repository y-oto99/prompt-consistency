# 検証ガイド

プロンプトに書かれた指示を同時に守れるか、操作の順序が変わっても公開の条件を守れるか、提案された操作に許可を出せるかを調べます。各節に、検証に使うデータ、実行方法、結果の読み方を記載しています。

## 自然言語の指示は両立するか

たとえば「なぜ改善したかを分かりやすく説明する」と「資料にない原因は断定しない」は、「原因が分からない理由を説明すればよい」と読むなら同時に守れます。「原因を特定する必要がある」と読む場合、資料に根拠がなければ衝突します。

| データ | 構成 | 確かめること |
| --- | --- | --- |
| 指示の配置を変えた9件 | 3組の指示をそれぞれ「2指示だけ」「同じ節に周辺指示を配置」「長い本文の離れた箇所に配置」の3段階で比較。 | 同じ指示でも、周辺の文章が増えたり指示が離れたりすると判定が変わるか。文の長さと指示間の距離は同時に変わる。 |
| 業務プロンプトの9件 | 計測相談、返品・配送、社内資料編集の3本に、それぞれ3つの入力状況を設定。 | 業務向けの指示一式から、入力に関係する例外や条件を読み取って、両立・衝突・解釈依存を区別できるか。 |
| 施設案内の6件 | 抽出指示の調整に使わない施設案内のプロンプト1本に、6つの入力状況を設定。 | 調整に使った3業務とは異なるプロンプトで判定を確かめる。6件は同じ業務の入力違い。 |

検査器は、与えられた読みごとに、必須・禁止・選択肢を論理式として扱います。すべての制約を満たす行動の組み合わせがあれば「両立」、なければ「衝突」です。両立する読みと衝突する読みがともにあれば「解釈依存」、結論に関わる変換漏れがある読みは「判定保留」です。検査の対象は抽出結果に記録された読みと制約です。「両立」の根拠として、制約を満たす行動の組み合わせを出力します。

リポジトリのルートで実行します。機械検査は保存済みの抽出結果を使います。原文の直接レビューを含む場合も、保存済みの判定を表示します。

```sh
python3 -m validation prompt --case research_full
python3 -m validation language
python3 -m validation holdout
```

| 出力項目 | 意味 |
| --- | --- |
| `expected` | 原文と入力状況に対する期待判定。[ケースごとの根拠](expectations.md)を参照。 |
| `structured` | 保存済みの抽出結果に対する機械検査。読みごとの判定、根拠となる行ID、両立する行動の組み合わせや衝突に関わる指示を表示する。 |
| `direct` | 原文と入力状況を構造化せずに直接レビューした判定。配置を変えた9件と業務プロンプトの9件に含まれる。 |
| `source_chars` | 行ID、見出し、改行を除いた本文の文字数。 |

`structured.initial` と `structured.revised` は、それぞれ [初版の抽出指示](extraction.md) と [改訂版の抽出指示](extraction_v2.md) に対応します。両者の原文、入力状況、期待判定、検査器は共通ですが、抽出担当も異なります。判定の差には、抽出指示と担当者の両方が関わり得ます。抽出担当と直接レビューの担当には原文と入力状況を渡し、期待判定を伏せています。直接レビューは各ケースにつき1回なので、出力は同じケースで判定を見比べるためのものです。

結果の根拠を確認するには、`prompt --case` の出力で該当する行IDを探します。ラベルが期待判定に一致していても、原文の義務をすべて抽出できたとは限りません。

## Leanで回答の再掲と情報開示を調べる

会員窓口の指示を二つ考えます。「前回の回答を求められたら、そのまま再掲する」「本人確認が有効なときだけ会員限定の文章を表示する」。最初の回答時には本人確認が有効でも、再掲時には期限が切れている場合があります。

[Disclosure.lean](formal/Disclosure.lean) では、一人の会員について、回答を「一般公開」か「会員限定」かの区分が付いた文章の列として表します。表示の可否は送信時に判定します。

- **元の指示が衝突する例**（`replay_after_expiry`）。一般向けの案内と会員限定の受付枠を含む回答案は、本人確認が有効なら送れます。確認が切れると、同じ案をそのまま再掲し、かつ限定部分を一切表示しない応答は存在しません。
- **再掲の指示に例外を明記した場合**（`filtered_replay_safe`）。「再掲時は現在の本人確認で許される部分だけを送る」と定めます。任意の長さ・内容の回答案について、この手順が出力する各部分は送信時の条件を満たすと証明します。
- **出力の確認**（`example_outputs`）。上の回答案では、本人確認が有効なら全文、無効なら一般向けの案内だけが残ります。

Lean 4.19.0 で `lean validation/formal/Disclosure.lean` を実行します。安全性は、本人確認の状態と各部分の区分が正しく与えられ、この送信手順を通ることが前提です。文章への区分付け、言い換えや推測を通じた漏えい、実際のLLMが指示に従うかは検査しません。

## 承認済みの版を公開する手順は成り立つか

編集・審査・公開予約を別々に進める場合、予約した後に原稿が更新されたり、承認が取り消されたりします。この検証では、公開する原稿が承認した版と予約した版の両方に一致し、公開時点でも承認が有効であることを求めます。公開できなくなった予約が残っても、手順を進めて公開にたどり着けるかも調べます。

個々の指示を一つの状況で比較するだけでは、どの時点の版や承認を参照するかが表れません。[状態遷移モデル](../checker/workflow_model.py)では、編集・審査・承認・取り消し・予約・公開・予約の解消を別々の操作として記述し、可能な順序を調べます。

| 手順 | 公開時の確認 | 失効した予約の解消 |
| --- | --- | --- |
| `queue_check_only` | 承認の確認は予約時のみ | なし |
| `bind_revision` | 公開版・承認版・予約版の一致 | あり |
| `guarded` | 版の一致と承認の有効性 | あり |
| `guarded_without_recovery` | 版の一致と承認の有効性 | なし |

**有限のモデル検査**では、版番号の上限を設定し、二つの性質を調べます。まず、公開条件に反する操作の順序があるかを探します。次に、到達可能な状態のどこからでも、公開へ進める経路が少なくとも一つあるかを調べます（CTLの `AG EF Published`）。後者が示すのは、適切な操作を続ければ公開できるという可能性です。

**SMTによる検査**では、別に記述した [SMT仕様](formal/approval.smt2) をZ3で調べます。初期状態と帰納ステップに反例がなければ、単一文書の版番号に上限を設けなくても、モデル上のどの到達状態でも公開条件が保たれます。公開まで進める経路の有無は、有限のモデル検査が扱います。

```sh
python3 -m validation workflow --bound 4
python3 -m validation.formal.run
```

有限のモデル検査で公開条件を破る順序がある場合は `counterexample` に、公開に進めない状態がある場合は `stranded_trace` に、そこまでの操作が表示されます。SMTでは `unsat` が反例なし、`sat` が反例ありを表します。版の一致だけを確認する操作についても、比較用の反例を出力します。

SMTの実行にはZ3の実行ファイルまたは共有ライブラリが必要です。実行ファイルがある環境では、`z3 -smt2 validation/formal/approval.smt2` で仕様を直接調べることもできます。結果が保証する範囲は、各モデルに記述された操作と条件です。

### Leanで公開条件を証明する

[Approval.lean](formal/Approval.lean) は、公開手順を Lean 4 で記述した独立の例です。状態として記録するのは現在の版、審査中・承認済み・予約済みの版、承認の有効性です。公開した時点でこれらの値を記録します。版番号には自然数を使い、上限を設けていません。

| 命題 | 確かめること |
| --- | --- |
| `guarded_safe` | 公開時に現在の版・承認版・予約版の一致と承認の有効性を確認する手順では、初期状態から何回操作しても、公開記録がこの条件を満たす。到達までの操作列について帰納法で証明する。 |
| `guarded_can_publish` | この手順で、版1の審査依頼・承認・予約を経て、実際に公開状態に到達できる。 |
| `revision_only_counterexample` | 版の一致だけを確認する手順では、版1を承認・予約し、承認を取り消した後も公開できてしまう。この操作列が反例になる。 |

Lean 4.19.0 で次を実行します。外部パッケージは使いません。Elanで版を指定する場合は `elan run leanprover/lean4:v4.19.0 lean validation/formal/Approval.lean` でも実行できます（初回は指定のツールチェーンをインストールしてください）。

```sh
lean validation/formal/Approval.lean
```

成功すると、3命題それぞれについて `does not depend on any axioms` と表示されます。有限モデル検査では到達できる状態を列挙し、Leanでは手作業で記述した遷移と命題に対する証明を型検査します。ここで証明したのはLeanのモデル内の公開条件です。Python実装との同値性や、どの状態からも公開に進めることは、この証明の対象外です。

## 提案された操作を許可できるか

プロンプトインジェクションへの防御では、利用者の依頼と資料に書かれた文を区別し、実際に操作を行う前に権限を照合します。この検証が扱うのは、出所や対象が構造化され、アプリ側で確認できる場合の操作の許可です。

| 確認の段階 | 確認すること |
| --- | --- |
| 資料の取り込み時 | 利用者からの依頼、文書やツールの結果など、情報の出所を区別する。資料本文の分類精度はこの検証の対象外。 |
| 操作の直前 | 許可ルールに従って依頼元、認証、操作・対象、公開先、公開区分、版、承認を照合する。アプリが判断に必要な事実を確定できなければ保留する。 |
| 応答を返す前 | 回答の根拠や情報の公開範囲を確認する。応答の検査はこの検証の対象外。 |

`boundary` は架空の22件で、認証を共通の前提に、確認範囲が「依頼元まで」「操作名まで」「操作対象・公開先・版・承認まで」の3方式を比較します。同じケースに対する許可（`allow`）、拒否（`deny`）、保留（`review`）の判定と理由を表示します。正当な要約と承認済みの公開のほか、対象からの逸脱、承認の失効、判断に必要な情報の欠落などを含みます。

`boundary-model` は、依頼元、認証、依頼と提案、公開区分、版、承認の値を定義した有限の範囲で組み合わせます。許可された操作が必要な権限を持ち、依頼や承認で指定された対象に限られているかを調べます。`first_violation` に条件を破る最初の組み合わせを表示します。該当する組み合わせがなければ `null` です。

この検査は、認証・依頼元・承認などをアプリ側で確定し、公開区分を信頼できる記録から取得できることが前提です。実際のアプリで操作の検査と実行の間に状態が変わり得る場合は、検査済みの版と実行対象を結び付ける必要があります。ここで使う22件は許可ルールを確かめるためのもので、攻撃成功率や文章からの検知率は計測しません。

```sh
python3 -m validation boundary
python3 -m validation boundary-model
```

外部資料と指示の分離、最小権限、操作の承認、出力の検査については [OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) と [OWASPの防御ガイド](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) を参照してください。
